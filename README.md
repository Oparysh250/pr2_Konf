# Граф зависимостей Alpine APK · вариант 14

Практическая работа по конфигурационному управлению, РТУ МИРЭА, ИКБО-18-25.

Утилита строит граф зависимостей Alpine Linux по метаданным APK
и открывает диаграмму в браузере. Пять этапов отмечены тегами Git
`stage-1` … `stage-5`.

## Запуск финальной версии

Нужны Python 3.11+, PlantUML, Java и Graphviz (`dot`). На Windows
команды можно выполнять в WSL. Если вместо команды `plantuml`
используется JAR, задайте абсолютный путь к нему.

```sh
# Вариант для запуска через JAR
export PLANTUML_JAR=/полный/путь/к/plantuml.jar
./run.sh --config examples/test.toml

# Проверка программы
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

На компьютере с установленной командой `plantuml` достаточно
выполнить `./run.sh --config examples/test.toml`.

Для показа отдельных этапов используйте команды из соответствующих
разделов после переключения на нужный тег.

```sh
git log --oneline --decorate --reverse
git switch --detach stage-1
./run.sh --config examples/test.toml
git switch main
```

## Этап 1. Конфигурация

Для запуска нужен Python 3.11+. Компиляция и пакеты Python не требуются.

```sh
./run.sh --config examples/test.toml
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

| Параметр TOML | Значение |
| --- | --- |
| `package` | Имя пакета APK или имя из прописных латинских букв в тестовом графе. |
| `repository` | HTTP(S) URL индекса Alpine или путь к графу относительно TOML. |
| `test_mode` | `true` для тестового графа, `false` для Alpine. |
| `filter` | Подстрока для исключения зависимостей с учётом регистра. Пустая строка выключает фильтр. |

Прототип печатает четыре поля в формате `ключ=значение`. Тесты
проверяют ошибки каждого поля, отсутствующий ключ и синтаксис TOML.

## Этап 2. Прямые зависимости Alpine

```sh
./run.sh --config examples/alpine.toml
```

Укажите URL каталога архитектуры или прямой URL `APKINDEX.tar.gz`.
Утилита скачивает архив, извлекает запись `APKINDEX` в память и читает
поля `P:` (имя), `D:` (зависимости и конфликты) и `p:` (предоставляемые
имена). Этап 2 выводит записи `D:` с ограничениями версий. Записи с
`!` выводятся отдельно как конфликты.

## Этап 3. Рекурсивный BFS

Тестовый граф хранит рёбра в TOML. Например, `A = ["B", "C"]`
задаёт зависимости A, а `B = []` описывает вершину без зависимостей.
Для каждого имени в правой части нужна отдельная запись.

```sh
./run.sh --config examples/test.toml
./run.sh --config examples/test-cycle.toml
./run.sh --config examples/test-filter.toml
```

| Сценарий | Порядок BFS | Особенность |
| --- | --- | --- |
| Общая зависимость | A, B, C, D, E | D обрабатывается один раз, оба ребра сохраняются. |
| Цикл | A, B, C, D | Ребро C → A сохраняется, повторного посещения нет. |
| Фильтр C | A, B, D | E исчезает вместе с единственным путём через C. |

`visit_queue` рекурсивно обрабатывает головы общей FIFO-очереди.
Имена помечаются посещёнными при добавлении. После 128 шагов внешний
цикл продолжает с той же очередью, ограничивая глубину стека и сохраняя
порядок BFS. Фильтр применяется до добавления соседа. Начальная вершина
входит в граф при любом фильтре.

В режиме Alpine `alpine_graph` связывает зависимости с именами
пакетов, используя поле `p:` для виртуальных имён вроде `so:libz.so.1`.
При нескольких поставщиках выбирается первый по имени, а зависимость,
которой нет в индексе, остаётся листом. Версии учитываются в выводе
этапа 2, а граф строится по именам из одного индекса без разрешения
ограничений версий и конфликтов.

## Этап 4. Обратные зависимости

`reverse_edges` меняет направление всех рёбер. Затем тот же
`breadth_first` обходит обратный граф. Прямые потребители находятся
за один переход, остальные попадают в общий список через другие
пакеты. Целевой пакет исключается из вывода даже при наличии цикла.

```sh
./run.sh --config examples/test-reverse.toml
./run.sh --config examples/test-reverse-filter.toml
./run.sh --config examples/test-cycle.toml
./run.sh --config examples/test.toml
```

| Пример | Прямые | Прямые и транзитивные |
| --- | --- | --- |
| D в обычном графе | B, C | B, C, A |
| D с фильтром B | C | C, A |
| A в графе с циклом | C | C, B |
| A в обычном графе | нет | нет |

## Этап 5. Визуализация PlantUML

```sh
./run.sh --config examples/alpine.toml
./run.sh --config examples/xz.toml
./run.sh --config examples/grep.toml
```

Утилита формирует `out/<пакет>.puml`, рендерит SVG и открывает
изображение в браузере. Стрелки идут от пакета к его зависимостям.
Голубым выделяется целевой пакет. В режиме `--no-open` программа
сохраняет оба файла без открытия браузера. В WSL сохранённые SVG
можно открыть через Проводник командой `explorer.exe out`.

### Сравнение с Alpine APK

Проверка выполнена через `apk dot` версии 2.14.13 по тому же индексу
Alpine v3.22, main, x86_64. Если в Alpine настроен этот репозиторий,
его вывод можно получить следующими командами.

```sh
apk dot zlib
apk dot xz
apk dot grep
```

| Пакет | Вершины PlantUML | Рёбра PlantUML | Рёбра apk dot | Связи |
| --- | ---: | ---: | ---: | --- |
| zlib | 2 | 1 | 1 | zlib → musl |
| xz | 3 | 3 | 3 | xz → musl, xz → xz-libs, xz-libs → musl |
| grep | 3 | 3 | 3 | grep → musl, grep → pcre2, pcre2 → musl |

После исключения версий из подписей DOT наборы рёбер совпали для всех
трёх пакетов. В выводе APK вершины подписаны именами с версиями,
а виртуальные зависимости указаны на рёбрах. Например, у ребра
`xz → xz-libs` есть подпись `so:liblzma.so.5`. PlantUML показывает
имена пакетов и объединяет повторные связи между одной парой вершин.
На индексах с несколькими поставщиками или ограничениями версий
полученный граф может отличаться от результата APK.
