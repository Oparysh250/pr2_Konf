## Этап 1. Конфигурация

Для запуска нужен Python 3.11+. Компиляция и пакеты Python не требуются.

```sh
./run.sh --config examples/test.toml
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

| Параметр TOML | Значение |
| --- | --- |
| `package` | Имя пакета APK или имя из прописных латинских букв в тестовом графе. |
| `repository` | HTTP(S) URL индекса Alpine или путь к графу относительно TOML. |
| `test_mode` | `true` для тестового графа, `false` для Alpine. |
| `filter` | Подстрока для исключения зависимостей с учётом регистра. Пустая строка выключает фильтр. |

Прототип печатает четыре поля в формате `ключ=значение`. Тесты
проверяют ошибки каждого поля, отсутствующий ключ и синтаксис TOML.

## Этап 2. Прямые зависимости Alpine

```sh
./run.sh --config examples/alpine.toml
```

Укажите URL каталога архитектуры или прямой URL `APKINDEX.tar.gz`.
Утилита скачивает архив, извлекает запись `APKINDEX` в память и читает
поля `P:` (имя), `D:` (зависимости и конфликты) и `p:` (предоставляемые
имена). Этап 2 выводит записи `D:` с ограничениями версий. Записи с
`!` выводятся отдельно как конфликты.

## Этап 3. Рекурсивный BFS

Тестовый граф хранит рёбра в TOML. Например, `A = ["B", "C"]`
задаёт зависимости A, а `B = []` описывает вершину без зависимостей.
Для каждого имени в правой части нужна отдельная запись.

```sh
./run.sh --config examples/test.toml
./run.sh --config examples/test-cycle.toml
./run.sh --config examples/test-filter.toml
```

| Сценарий | Порядок BFS | Особенность |
| --- | --- | --- |
| Общая зависимость | A, B, C, D, E | D обрабатывается один раз, оба ребра сохраняются. |
| Цикл | A, B, C, D | Ребро C → A сохраняется, повторного посещения нет. |
| Фильтр C | A, B, D | E исчезает вместе с единственным путём через C. |

`visit_queue` рекурсивно обрабатывает головы общей FIFO-очереди.
Имена помечаются посещёнными при добавлении. После 128 шагов внешний
цикл продолжает с той же очередью, ограничивая глубину стека и сохраняя
порядок BFS. Фильтр применяется до добавления соседа. Начальная вершина
входит в граф при любом фильтре.

В режиме Alpine `alpine_graph` связывает зависимости с именами
пакетов, используя поле `p:` для виртуальных имён вроде `so:libz.so.1`.
При нескольких поставщиках выбирается первый по имени, а зависимость,
которой нет в индексе, остаётся листом. Версии учитываются в выводе
этапа 2, а граф строится по именам из одного индекса без разрешения
ограничений версий и конфликтов.
